# JSON backups and reconciliation

Ticket: `.scratch/first-usable-version-build/issues/04-json-backup-and-merge.md`.

The task is to back up or transfer a collection, review an imported file before changing data, and recover the previous collection after a complete replacement. Success preserves factual values, stable IDs, unknowns, units, date precision, item tracking settings and deletion markers. There is no schema change or development-data reset.

## Public interfaces

The approved seams remain History, Calculations, Storage and browser workflows. Storage owns reconciliation, serialization and persistence; Interface owns file selection, review choices and downloads. The codebase-design vocabulary guided this interface: callers receive complete operations without coordinating IndexedDB requests or manipulating record arrays.

- `serialize(collection)` / `deserialize(json)` use History's strict schema contract. Supported schemas 1–3 migrate to schema 4 through the existing implementation. Unknown versions, fields, record kinds, types, duplicate IDs and missing references fail before preview or any write. Only collection data is serialized: selected vehicle, theme, local revision, account/Gist bindings and credentials are not portable collection fields. Vehicle unit preferences and item tracking settings are portable.
- `previewMerge(current, incoming)` validates both entire collections and returns detached additions, conflicts, matching count and a different-collection flag. It does not mutate or save. `applyMerge(current, incoming, choices)` revalidates and returns a detached validated candidate; choices are indexed by stable ID. These pure public operations can also consume collections fetched from a future Gist adapter. Baseline-aware three-way reconciliation remains ticket 13.
- Independent records combine; equal records deduplicate regardless of object-property order. Absent records do not imply deletion. Retained markers conflict with live records, and two deletion markers of the same kind retain the local marker without treating differing deletion timestamps as a live-content conflict. Different collection IDs can merge while retaining the local collection identity. Labels/dates never establish identity. Cross-kind ID collisions and collection/record ID collisions are refused.
- Every divergent same-ID vehicle requires a choice. `local` / `incoming` select that complete vehicle branch, including linked items/history and known cascade markers. If both vehicles are live, `merge-local` / `merge-incoming` explicitly confirm the same vehicle and choose its details while independently reconciling history. Timestamp collisions never silently combine histories. Item edit/delete conflicts similarly resolve their linked history as a group. A selected parent deletion also marks descendants newly added on the other side. Whole-branch choices suppress subordinate conflict controls; choosing to combine exposes them again. Incompatible cross-reference choices fail final History validation without a write.
- `createLocalStorage().replace(candidate, recovery)` checks the expected local revision and writes recovery then active data in one read/write transaction. Aborting either write aborts both. Recovery includes the current in-memory collection (including recorded changes whose earlier save failed), selection and revision. `loadRecovery()` returns the last successful replacement's recovery snapshot or null; it uses the same validation as active data. Only a successful later replacement replaces this copy, as stated beside the action. No database-version change is needed: the existing store gains a `recovery` key.
- Import/replacement commits retain the old in-memory snapshot and review choices until transaction completion. Failure leaves the preview open for correction/retry and keeps Export JSON usable. A stale-tab revision fails without overwriting current data or recovery. No successful-save message appears before commit. File reads and writes serialize UI actions to prevent overlapping previews/applies. Complete replacement is separate, explicitly confirmed, and uses the validated file regardless of merge choices.
- A file that passes independent schema validation but cannot coexist with current IDs remains available for recoverable replacement. Its complete contents are listed, the merge incompatibility is explained, and only Merge import is disabled. Invalid files expose neither action.
