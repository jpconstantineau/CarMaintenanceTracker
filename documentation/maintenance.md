# Maintenance items and due intervals

Issue: `.scratch/first-usable-version-build/issues/03-maintenance-items-and-due-intervals.md`.

The owner can select an applicable common item or create a custom item, retain replacement information, record completed work separately from inspection, and review the next configured distance/date with its supporting history. No item or interval is installed automatically. The existing Other maintenance and Check / inspect actions now offer the vehicle's items before date/mileage entry. Item details also offer named service and inspection actions.

## Module contracts and retained data

The four modules remain History, Calculations, Interface and Storage. The approved test seams in the source specification remain unchanged.

- History adds `listItems(collection, vehicleId)`, `saveItem(collection, vehicleId, details, itemId?)` and `removeItem(collection, itemId)`. Reads are detached; writes validate an entire candidate without mutating the original. Items have UUID identity, vehicle ownership, name, specifications, compatible part numbers, preferred brand, notes, HTTP(S) reference links, tracking settings, and edit metadata. URLs with credentials or executable schemes are refused. Confirmed item deletion removes its linked factual records and preserves tombstones for every removed identity; unassigned records and other items/history remain unchanged. The confirmation identifies the item and number of linked records before removal.
- Schema **4** adds `items` to the collection. Maintenance and observation records add `itemId`, `action`, `partUsed`, and optional `{amount, currency}` cost. Null references preserve unassigned historical notes. A linked action must have nonblank action text and the same owning vehicle as its item. Only kind `maintenance` qualifies as completed service. Cost is descriptive, nonnegative, and carries a three-letter currency; it is never summed or converted.
- Tracking is `{distance: null | {value, unit}, months: null | integer, condition: null | {metric, unit, operator, threshold}}`. All-null means history only. Distance is positive in km/mi; elapsed time is 1–1200 whole calendar months. Condition settings retain the user's named metric, units, nonnegative threshold and inclusive comparison (`at-or-below` / `at-or-above`). The contract permits combinations. Condition-specific measurements/formulas belong to subsequent oil/tire slices; this slice explicitly reports condition results unavailable.
- Calculations adds `maintenanceSummary(collection, vehicleId, asOf)`, with an exact evaluation date supplied by Interface using the local calendar. Results include item history, last qualifying service identity, due mileage in vehicle units, due-date bounds, state and reasons. They are never saved. Distances use original units and exact conversion constants; only the display rounds.
- Last service uses the same private chronology comparator as the vehicle timeline: recorded date bounds, then consistent odometer evidence for overlapping dates. Converted readings within `1e-8` are equivalent and cannot establish order. A contradiction involving either record disables inferred mileage ordering, including contradictions with a third record. Ambiguous service order withholds a baseline. Known maintenance gaps overlapping/following the baseline withhold dependent due results. Conflicting mileage withholds distance results, and evidence extending after the evaluation date cannot establish distance status. A time threshold can still independently establish due status when service order is established by dates alone.
- Calendar addition clamps to the target month's last day, including leap years. Month/year precision produces earliest/latest dates; no day is written back to history. Either threshold establishes `due`; an evaluation inside a due range is `uncertain`. A missing baseline or unevaluable condition is `unavailable`, unless another threshold already establishes due. Inspections and year boundaries never restart an interval.
- Storage retains IndexedDB version 1 / `workspace` / `active`, with its existing transaction and stale-revision protection. Versions 1–3 validate against their own shape before migrating to v4; all prior identities, values, units, unknowns, notes and deletion markers remain. No data reset occurs. Vehicle deletion also tombstones/removes its items. Unsupported input or ordinary save failure does not clear data.
